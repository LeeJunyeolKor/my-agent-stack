# 코드 리뷰

검토 대상의 계약과 실제 동작이 어긋나는 지점을 찾는다. 심각도는 발생 조건과 사용자 영향으로 설명하고, 취향·선택적 개선과 결함을 구분한다. 로컬 diff만 있는 프로젝트에서도 시작할 수 있다.

## 조사

1. 저장소 지침과 변경 범위를 읽고 대상 브랜치·기준 리비전·diff를 고정한다. 다른 브랜치에서 읽은 줄 번호를 근거로 쓰지 않는다.
2. PR이 있으면 목적과 기존 논의를 확인한다. 연결된 요구사항은 접근할 수 있을 때 대조한다. 티켓이 없으면 요구하지 않고 이 비교를 생략한다. 조회 실패는 요구사항이나 PR이 없다는 뜻이 아니다.
3. 변경된 값과 옵션을 선언·주입에서 실제 소비까지 추적한다. 공용 인터페이스나 데이터 형식이 바뀌면 소비처와 회귀 검증으로 조사 범위를 넓힌다.
4. 판단을 바꾸는 기술적 주장은 대상 버전의 설치본·설정·테스트 또는 공식 자료로 확인한다. 저장소 밖 환경이 전제인데 확인할 수 없으면 그 지적은 보류하고 필요한 사실을 알린다. 추측을 결함으로 게시하지 않는다.
5. 적절한 검증 수단이 있으면 격리된 환경에서 재현한다. 실행할 수 없으면 확인한 코드 근거와 미검증 동작을 구분한다. “리뷰만” 요청에서 수정, 커밋, 게시를 실행하지 않는다.

## 판단

- 수치·기본값은 이전 값과의 실효 차이를 계산하고 실제 적용 조건을 확인한다.
- 인터페이스는 입력의 누락·우선순위·중복과 소비자의 기대를 비교한다. 빈 문자열·0·false가 유효한 값인지 확인한 뒤 폴백 연산자를 판단한다.
- 비동기 작업은 시작 순서와 완료 순서가 다른 경우, 소유자가 사라진 경우, 재시도가 겹친 경우의 상태를 추적한다.
- 마이그레이션은 옮긴 코드뿐 아니라 사라진 예외 분기와 대체 경로를 확인한다. 의존성은 선언 범위와 lockfile의 실제 버전을 구분한다.
- 구조 개선은 구체적인 오류 가능성이나 다음 변경의 비용을 설명할 수 있을 때 제안한다. 새 추상화와 캐시를 취향으로 요구하지 않는다.
- 테스트는 이름보다 실제 검증하는 계약을 읽는다. 녹색 결과가 이번 회귀 경로를 실행했는지 확인한다.

스택 PR이면 대상 브랜치 관계로 순서를 복원한다. 동작을 도입한 PR에 근거를 연결하고, 누적 변경에서만 생기는 문제는 합쳐진 결과를 확인한다. 각 지적의 리비전과 위치를 다시 확인한다.

## 결과

문제별로 우선순위, 발생 조건, 관찰한 코드, 영향, 권장 수정 방향과 검증 범위를 보고한다. 수정 방향은 정확성·가독성·유지보수를 기준으로 고른다. 발견 사항이 없더라도 남은 검증 공백을 적는다.

댓글을 다듬거나 게시해 달라는 요청이 있으면 이 결과를 review-comment에 전달한다. 승인된 결론을 표현 편집만으로 강화하지 않는다. 도구가 없으면 로컬에서 확인한 범위까지 보고하고 원격 조회·게시를 실행한 것처럼 말하지 않는다.
