# 코드 동작 설명

독자가 알고 싶은 동작부터 답한다. 한국어 표현·용어와 의미 보존은 [technical-writing](../technical-writing/SKILL.md)을 함께 적용한다. 코드 조사와 동작 설명은 이 스킬이 맡고, 결함의 타당성 판단은 code-review, 조사 결과의 기간·집계·보고서 구성은 report-writing이 맡는다. 이 둘을 설명 요청의 필수 단계로 실행하지 않는다.

## 조사 범위와 근거

1. 질문, 제공된 코드, 독자 수준과 대상 저장소의 AGENTS.md·설정을 확인한다. 짧은 함수면 그 함수와 이해에 필요한 타입·직접 호출만 읽는다. 저장소 전체 조사나 문서 파일 생성을 기본값으로 삼지 않는다.
2. 기능 설명이면 실제 진입점에서 호출자 → 중간 계층 → 데이터·상태 소유자 → 소비처를 추적한다. 이름이나 import만으로 실행 경로를 단정하지 말고 조건, 인자와 반환값을 연결한다. 선택되는 구현은 설정·등록·라우팅 근거로 확인한다.
3. 핵심 주장에 파일 경로, 심볼, 확인한 리비전을 붙인다. 미커밋 변경을 읽었다면 HEAD와 작업 파일의 차이를 밝힌다. Git이 없거나 코드가 대화에만 있으면 제공된 코드 기준이라고 적고 리비전을 만들지 않는다.
4. 변경 전후 요청은 base와 head를 확인하고 같은 입력·조건으로 비교한다. 이전 구현을 못 읽었으면 현재 코드만으로 과거 동작을 재구성하지 않는다.
5. 외부 라이브러리·시스템은 설치 버전, 설정과 공식 자료에서 확인한 범위까지만 설명한다. 소스만 읽은 결과와 실행 관찰을 구분한다. 도구나 자료가 없으면 확인한 경계와 남은 질문을 알린다.

## 설명을 연결하기

- 목적과 사용자에게 보이는 결과를 먼저 쓰고 입력 → 처리 → 출력을 연결한다. 여러 계층의 흐름은 실제 중간 호출을 건너뛰지 않는다.
- 동작을 이해하는 데 필요한 상태 소유권·수명, 비동기 시작·대기·완료 순서와 실패·폴백 분기를 설명한다. 실패가 상위로 전파되는지, 복구되는지, 기존 상태가 남는지 코드를 근거로 구분한다. 확인되지 않은 경쟁 방지나 재시도를 덧붙이지 않는다.
- 구현된 사실, 설계 의도에 대한 추론, 미확인을 구별한다. 이름·주석·작성자의 설명은 의도를 추정하는 자료이며 실행 증거와 같지 않다. 실행하지 않은 테스트를 통과했다고 쓰지 않는다.
- 비유·예제에는 설명용이라는 표시를 붙이고 실제 구현의 조건과 다른 점을 가까이 적는다. 도식은 관계·순서·분기가 글보다 잘 보일 때 사용한다. 짧은 함수에 구조도를 강제하지 않는다.
- 짧은 질문은 대화 안에서 답한다. HTML 설명 문서를 요청하면 [HTML 형식](references/html-format.md)을 읽고 [자체 포함 템플릿](assets/explainer.html)을 바탕으로 작성한다. 문서의 내용과 길이는 질문에 맞게 바꾸되 지정된 시각 형식을 유지한다.

## 실행 경계와 마무리

“설명만”은 읽기와 답변 범위다. 코드·파일·Git index·HEAD를 바꾸거나 테스트를 실행하거나 커밋·외부 게시하지 않는다. HTML 파일 작성 요청은 해당 산출물의 저장만 허용하며 설명 대상 코드를 수정할 권한으로 확대하지 않는다. 게시 요청은 별도 도구와 권한을 확인한다.

설명을 마치기 전에 실제 호출과 조건이 이어지는지, 근거보다 강한 주장이 없는지 확인한다. 핵심 제한은 접는 상세 안에만 숨기지 않는다. 결과와 근거, 실행한 확인과 미검증을 짧게 남긴다.
