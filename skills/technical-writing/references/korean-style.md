# 한국어 문체 기준

한국어 초안을 쓰거나 고칠 때 읽는다. 대상 저장소나 팀에 정해진 문체 규칙이 있으면 그 규칙이 먼저다. 이 문서는 정해진 규칙이 없을 때 쓰는 기본값이다.

문장을 통제하는 규칙(용어 고정, 문장당 지시 하나 등)은 영어 기술 문서 규칙인 ASD-STE100(Simplified Technical English)의 생각을 한국어에 맞게 옮긴 것이다. 숫자로 적은 한도는 문장을 다시 읽어 볼 신호로 쓴다. 한도를 맞추려고 한국어가 어색해지면 한도를 넘긴다.

## 1. 용어

- 줄임말을 쓰지 않는다. "클라" 대신 "클라이언트", "레포" 대신 "저장소"로 쓴다.
- 한국어 글에서 이미 자리 잡은 외래어(페이지, 브랜치, 커밋, 컴포넌트)는 그대로 쓴다. 억지로 우리말로 바꾸지 않는다.
- 코드 식별자, 제품 이름, 필드 이름, 업계에서 원어로 쓰는 용어(LLM, API 등)는 원래 표기를 지킨다.
- 개념 하나에 용어 하나를 쓴다. 문서 앞에서 "사용자"라고 했으면 뒤에서 "고객"이나 "회원"으로 바꾸지 않는다. 반대로 같은 단어가 두 개념을 가리키면 하나를 다른 말로 나눈다.
- 절차의 동작을 가리키는 동사는 용어처럼 고정한다. "설치"라고 쓰기 시작했으면 같은 동작을 "세팅"이나 "구성"으로 바꿔 부르지 않는다. 설명하는 문장의 일반 동사는 반복을 피하려고 바꿔도 된다.

## 2. 번역투

- 영어 용어를 글자 그대로 옮기지 않고 무슨 일이 일어나는지 쓴다. 예: retry with backoff를 "백오프와 함께 재시도한다"로 쓰지 않고 "실패하면 기다리는 시간을 점점 늘리며 다시 시도한다"로 쓴다.
- 영어 관용 비유를 그대로 옮기지 않는다. 예: "이 함수가 병목의 심장이다" → "이 함수에서 시간이 가장 많이 든다".
- "형용사 + 추상명사" 꼴의 직역을 푼다. 예: "높은 가시성을 제공한다" → "어디서 실패했는지 바로 보인다".
- 영어 문장 하나를 한국어 문장 하나에 맞추지 않는다. 길면 나누고, 조각나면 합치고, 어순은 한국어를 따른다.
- 뜻 없는 동사를 뺀다. "진행하다", "수행하다", "실시하다"는 실제 동작을 가리키는 동사로 바꾼다. 예: "검토를 진행했다" → "검토했다", "마이그레이션을 수행한다" → "데이터를 새 테이블로 옮긴다". "~을 통해"는 "~로"로 충분하면 줄인다.
- 이중 수동("~되어지다")과 영어식 진행형("~되고 있다")을 피한다. 예: "로그가 수집되어지고 있다" → "로그를 모은다". 상태를 설명하는 "~된다"는 자연스러우면 그대로 둔다.
- 줄표(—) 뒤에 이유나 설명을 이어 붙이지 않는다. 예: "캐시를 끈다 — 오래된 값이 보이기 때문" → "캐시를 끈다. 오래된 값이 보이기 때문이다."

## 3. 문장과 문단

- 명사를 세 개 넘게 잇지 않는다. 예: "사용자 권한 변경 이력 조회 화면" → "사용자 권한이 바뀐 이력을 보는 화면".
- 절차는 한 문장에 지시 하나만 둔다. 문단 하나에는 주제 하나만 두고, 길어도 여섯 문장 안팎에서 끊는다.
- 행동하는 사람이 바뀌거나 여럿이면 주어를 쓴다. 예: "승인 후 배포" → "팀장이 승인하면 담당자가 배포한다". 목록과 표에서는 제목이나 열 이름이 주어를 대신한다.
- 경고는 해야 할 일을 먼저 쓰고 이유를 뒤에 쓴다. 예: "작업 중에는 노트북을 닫지 않는다. 동기화가 중간에 끊긴다."
- 동작 원리를 괄호 속 코드 이름에 기대 한 문장으로 압축하지 않는다. 경로마다 무엇을 하고 왜 중요한지 풀어 쓰고, 여럿이면 번호를 붙인다.
- 목록이나 표를 소개하는 문장에 개수를 쓰면 실제 항목 수와 맞춘다. 숫자만 쓰지 말고 무엇의 개수인지 쓴다. 예: 단계가 다섯 개인 표 → "다음 다섯 단계".

## 4. 목록과 표 칸

본문 문체와 관계없이 목록 항목과 표 칸은 어미 없이 끊는다. 부정은 "없음", "아님"으로 끝낸다.

| 고치기 전 | 고친 뒤 |
| --- | --- |
| 설정 파일을 읽어 옵니다. | 설정 파일 읽기 |
| 재현 방법을 찾지 못했습니다. | 재현 방법 찾지 못함 |
| 이번 변경과 관련이 없습니다. | 이번 변경과 관련 없음 |

## 5. 링크

- 다른 자료를 가리킬 때는 ID나 "여기" 대신 자료의 제목에 링크를 건다. 본문 중간에 언급할 때도 같다.
- 링크는 자료를 읽는 동안 챙긴다. 다 쓴 뒤 다시 찾지 않는다.
- 제목만으로 상태나 관련성이 드러나지 않으면 짧게 덧붙인다. 예: `— 더 이상 쓰지 않음`, `(2026-03 기준)`.
- 코드 위치는 `경로/파일.ext:줄` 형태로 쓴다. 리뷰 중인 변경이 있으면 그 변경의 해당 줄 링크를 함께 준다.
- 다른 사람과 함께 보는 곳(이슈, 위키, 메신저)에는 작성자 컴퓨터에만 있는 파일을 인용하지 않는다. 다른 사람이 열 수 없다면 핵심 내용을 본문에 직접 쓴다.

## 6. 글 종류별 문체 기본값

대상 저장소나 팀 관례가 없을 때 쓴다. 기존 문서를 고칠 때는 그 문서가 이미 쓰는 문체를 따른다.

| 글 종류 | 문장 문체 |
| --- | --- |
| 커밋 메시지, 코드 주석, 테스트 이름 | 평서체("~한다") |
| PR 설명, 이슈 | 합쇼체("~합니다") |
| 위키 문서, 공유용 산출물 | 합쇼체 |
| 사용자와의 대화 답변 | 합쇼체 |

## 7. 사용자와의 대화 답변

- 사용자가 바로 판단할 수 있게 풀어 쓴다. 항목마다 무엇이고 왜 중요한지 쓰고, 여럿이면 번호를 붙인다.
- 8장의 줄여 쓰기 규칙은 대화 답변에 적용하지 않는다.

## 8. 공유용 산출물

작업 맥락을 모르는 사람(다른 팀, 의사결정자)이 읽는 문서, 보고 페이지, 대시보드에 적용한다.

- 그 문서만 읽어도 이해되게 쓴다. 작성 중의 대화나 개인 메모를 가리키지 않는다.
- 설명 문단보다 구조를 먼저 쓴다. 표, 목록, 링크가 이미 보여 주는 내용을 문장으로 다시 말하지 않는다. 소개 문장과 방법 설명은 구조만으로 부족할 때만 넣는다.
- 제목은 대상의 이름만 쓴다. 한 줄 소개가 필요하면 명사구로 쓴다.
- 열 이름과 라벨은 한두 단어의 명사로 쓴다. "무엇을 했나" 같은 질문형 머리글을 쓰지 않는다.
- 제목, 라벨, 표 칸, 툴팁에서 같은 개념에 같은 용어를 쓴다.
- 표 칸과 상세 항목은 4장처럼 끊어 쓴다. 행동하는 사람이 중요하면 항목마다 쓰지 않고 열 이름이나 블록 제목에 둔다.
- 이슈 번호나 이슈 제목을 그대로 옮기지 않는다. 단계와 작업 흐름 단위로 무엇이 끝났고, 무엇이 남았고, 언제 끝나는지 쓴다.
- 같은 정보를 두 곳에 두지 않는다. 겹치면 합치거나 각자의 역할을 나눈다.
- 기간은 영업일로 쓴다. 예: `5 영업일`.
- 참고 자료는 링크 두세 개만 목록으로 두고 설명을 붙이지 않는다.

| 고치기 전 | 고친 뒤 |
| --- | --- |
| 모바일 앱 로그인 개선 프로젝트 진행 경과 보고 | 모바일 앱 로그인 개선 |
| 아래 표는 이번 분기에 끝낸 작업과 남은 작업을 정리한 것입니다. | (삭제. 표가 보여 줌) |
| 열 이름: 어떤 점이 달라졌나요? | 열 이름: 변경 |
| 간편 로그인 화면을 새로 만들고 기존 화면을 정리했습니다. | - 간편 로그인 화면 추가<br>- 기존 로그인 화면 정리 |

## 9. 내보내기 전 확인

- 줄임말
- 직역한 용어와 비유
- 뜻 없는 동사, 이중 수동, 줄표 뒤 설명
- 대화 답변에서 지나치게 압축한 설명
- 글 종류에 맞는 문체
- 링크 없이 남은 ID나 작성자 컴퓨터의 경로
