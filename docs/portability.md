# 이식성과 이름 규칙

<a id="portable-core"></a>
## 이식 가능한 핵심 구조

이식 가능한 구성 요소는 특정 조직의 제품 선택이나 용어에 의존하지 않고 문제, 필요한 기능, 권한, 실패 시 동작, 검증 방법을 설명합니다.

도구 제품은 프로필에서 선택합니다.

```json
{
  "providers": {
    "scm": "github",
    "issues": "none",
    "messaging": "none"
  }
}
```

회사를 옮길 때는 이식 가능한 워크플로를 수정하는 대신 새 로컬 프로필이나 프로바이더 어댑터를 사용해야 합니다.

<a id="neutral-public-names"></a>
## 중립적인 공개 이름

공개 ID는 회사, 팀, 저장소, 내부 프로그램이 아니라 기능을 설명해야 합니다. 기존 비공개 구성 요소를 일반화할 때는 다음 원칙을 따릅니다.

1. 공개 ID에서 조직별 프리픽스(prefix)를 제거합니다.
2. 프리픽스를 제거한 결과가 모호하다면 역할이 더 분명한 이름을 사용합니다.
3. 공개 메타데이터와 예시에서 기존 비공개 ID를 제거합니다.
4. 지침, 스크립트, 픽스처(fixture), 과거 맥락에 묶인 문서에 내부 정보가 남아 있는지 검사합니다.
5. 정규화한 이름이 충돌하면 작업을 중단합니다. 공개 ID가 같다는 이유만으로 구성 요소를 합치지 않습니다.

예시:

```text
비공개 프리픽스 + review-comment  → review-comment
비공개 프리픽스 + ticket-update   → issue-status-sync
```

비공개 설치 이름과 공개 이름의 매핑은 이 저장소가 아니라 Git에서 무시되는 로컬 마이그레이션 파일에만 둡니다.

<a id="installation-portability"></a>
## 설치 이식성

프로젝트 범위는 저장소 체크아웃을 대상으로 합니다. 사용자 범위에서는 `--target`을 사용자의 홈 디렉터리로 취급합니다. 지정한 대상이 모호하더라도 CLI가 다른 홈 디렉터리, 저장소, 조직을 임의로 추론하지 않습니다.

복사 방식은 제품이 달라도 결과를 예측하기 쉬우므로 기본값으로 사용합니다. 향후 개발 전용 링크 모드를 추가하더라도 반드시 선택형(opt-in)으로 제공해야 하며, 심볼릭 링크 지원 여부를 문서화하지 않은 대상도 고려해야 합니다.
